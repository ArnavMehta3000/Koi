# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

Tradeoff: These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## Overview

Koi is a Windows-only C++23 game engine built on Direct3D 12. The build system is **xmake** (3.0.8+). There is no test framework in the repo.

## Build & Run

```powershell
xmake                       # build (default mode: debug)
xmake run koi-runtime       # build + run; runargs are auto-set to "-p Sandbox/Sandbox.toml"
xmake build Koi.Engine      # build a single target (Koi.Engine | Sandbox | koi-runtime)
```

Switch build mode by reconfiguring, then building:

```powershell
xmake f -m release          # modes: debug | release | releasedbg | profile
xmake
```

- `run.autobuild` is on, so `xmake run` rebuilds first.
- `plugin.compile_commands.autoupdate` keeps `compile_commands.json` current for tooling.
- `profile` mode defines `KOI_ENABLE_PROFILING=1`, which enables Tracy (`TRACY_ENABLE`).
- Set the compile-time log floor with the `LogLevel` option: `xmake f --LogLevel=2` (0=trace … 4=error).

## Targets & layout

- **`Koi.Engine`** (`Engine/`) — static library, the engine itself. Public include root is `Engine/`, so includes are written relative to it (`#include "Core/Logger.h"`, `#include "Graphics/RHI/Device.h"`).
- **`Sandbox`** (`Sandbox/`) — static library holding the *game/application* code. Gameplay lives in `Sandbox/Scripts/` (e.g. `SandboxApp.cpp`); assets in `Sandbox/Assets/{Shaders,Models}`.
- **`koi-runtime`** (`Launcher/`) — the executable. Links `Koi.Engine` + `Sandbox`. In `debug`/`releasedbg` it builds as a console app; otherwise as a `win.sdk.application` (WinMain) that allocates its own console.

Xmake config lives in `Xmake/`: `Packages.lua` (deps), `Options.lua` (`LogLevel`), `Rules.lua` (`GenerateRDI`, `Natvis`), `ConfigFiles/*.h.in` (generated headers), `Packages.lua` (includes the various packages being used in the project. Custom package definitions live in `Xmake/Packages` which contains xmake compatible lua scripts).

## Architecture

### Application lifecycle
Entry is generated by the `KOI_IMPLEMENT_MAIN()` macro (`Engine/Runtime/EntryPoint.h`) — pick `KOI_DEF_MAIN` vs `wWinMain` based on build mode. It calls `koi::internal::RunApplication`, which:
1. Constructs the `Engine` (singleton via `Engine::Get()`).
2. Calls the user-provided factory `koi::CreateApplication(cmd)` — **the game must implement this** (see `Sandbox/Scripts/SandboxApp.cpp`). It returns a `std::unique_ptr<AppBase>`.
3. Runs `Engine::RunApp(app)`.

Game code subclasses `AppBase` (`Engine/Runtime/AppBase.h`) and overrides `OnInit/OnShutdown/OnTick(dt)/OnRender`. `AppBase` and `Engine` are both singletons (`::Get()`). `AppBase::GetDesc()` exposes the `AppCreateDesc` (window size, startup scene path, app name) set during `CreateApplication`.

The main loop (`Engine::MainLoop`) is: `BeginFrame` (poll window events, destroy closed windows, `Renderer::BeginFrame`) → `Tick` (`app.OnTick` then `app.OnRender`) → `EndFrame` (`Renderer::EndFrame`, advance frame index). Loop exits when all windows close or `Engine::RequestExit()` is called.

### Graphics (RHI over DX12)
- `GfxDevice` (`Graphics/RHI/Device.h`) owns the D3D12 device, queues, fences, root signature, and four `DescriptorHeap`s (RTV/DSV/resource (bindless CBV/SRV/UAV)/sampler). It creates/destroys `Texture`/`Buffer`/`Pipeline` resources, each stored in a `HandlePool` and referenced by a typed handle.
- **Resource lifetime is fence-based deferred deletion.** `Destroy(handle)` queues the resource against the current fence value; it's only freed once the GPU passes that fence (`FlushDeferredDeletions`). Don't free GPU resources synchronously.
- `Renderer` (`Graphics/Renderer.h`) owns the `GfxDevice`, a `HandlePool<RenderWindow>`, and per-window `FrameContext` (command allocator + list). Window resize/close are wired via callbacks in `Engine::RegisterWindowWithRenderer`.
- DX12 type aliases (`dx12::Device`, `dxgi::Factory`, `ComPtr`, etc.) live in `Graphics/DX12/DX12Common.h`.
- `Renderer::GetDefaultResources()` returns `RendererResources` — a 1×1 white texture, flat-normal texture, and three pre-built samplers (`LinearWrapSampler`, `LinearClampSampler`, `PointClampSampler`) identified by `DescriptorIndex`. Use these as fallbacks when a mesh has no texture.
- Render targets use an HDR color buffer (`RenderWindow::GetHDRColorBuffer()`, `R16G16B16A16_FLOAT`) which is tonemapped to the swapchain during `Renderer::EndFrame`. `OnRender` should target this buffer, not the swapchain directly.

### Handles & pools (`Engine/Core/Handle.h`)
The core data-structure pattern across the engine. `Handle<T>` is a generational handle (packed index + generation, default 20+12 bits). `HandlePool<T>` (dynamic) and `StaticHandlePool<T, N>` (fixed-capacity, placement-new) are sparse→dense pools: erasing bumps the slot generation so stale handles fail `IsValid`/`Get` (returns `nullptr`). Pointers returned from `Get()` are not stable across insert/erase — store handles, not pointers.

### Memory tracking (`Engine/Memory/`)
Global `operator new`/`delete` are overridden in `MemoryOverrides.cpp` to record allocations against a **thread-local tag stack**. Wrap a scope with `KOI_MEM_TAG_SCOPE(MemTag::Renderer)` to attribute allocations (tags in `MemoryTags.h`). Stats go to `MemoryTracker` (singleton) and to Tracy. The engine snapshots tagged memory at startup and prints the diff on shutdown to surface leaks.

### Logging (`Engine/Core/Logger.h`)
Use `KOI_LOG_TRACE/DEBUG/INFO/WARN/ERROR/CRITICAL(fmt, ...)`. The log **category is the current filename** (`KOI_FILE`), so each file logs under its own name automatically. Levels are gated at compile time by `KOI_LOG_LEVEL` (from the `LogLevel` xmake option) *and* at runtime by spdlog. Backed by spdlog with file (`Logs/Koi.log`), MSVC debug, and console sinks. `Logger::Init()` must run before any log call (the engine does this first).

### Generated config (`Engine/Core/Config.h`)
`Version.h` and `LogLevel.h` are generated at build time from `Xmake/ConfigFiles/*.h.in` into `$(builddir)/Generated/...`. Always go through `Core/Config.h`, which also defines `KOI_DEBUG`/`KOI_RELEASE`/`KOI_PROFILING`. Include `Core/Core.h` for the common bundle (`Config.h` + `Types.h` + `Macros.h`).

### Scene system (`Engine/Scene/Scene.h`)
`Scene` holds a flat `std::vector<SceneNode>` (BFS-topological order, so parent index < child index) and a `std::vector<GPUMesh>`. Load from a TOML file via `Scene::Load(path, device, fallbackAlbedoSRV)` — returns `std::optional<Scene>`. Call `Scene::Update()` once per frame to recompute dirty world transforms; `Scene::Release(device)` defers GPU buffer destruction through the fence system.

Scene TOML format (see `Sandbox/Assets/Scenes/Main.toml`):
```toml
[[nodes]]
name     = "MyNode"
parent   = "ParentName"    # optional; links to another node by name
mesh     = "Assets/Models/Foo.gltf"  # optional; omit for transform-only nodes
position = [x, y, z]
rotation = [x, y, z]      # degrees — converted to radians internally (ZXY order)
scale    = [x, y, z]
```
Meshes are deduplicated by path. The `startup_scene` key in `Sandbox.toml` points to the scene file loaded at startup.

### Transform & math
`Transform` (`Engine/Core/Transform.h`) stores `Position`, `EulerAngles` (radians, ZXY order), and `Scale`. `ToMatrix()` returns a `math::float4x4`. The math library is **hlslpp** (`koi::math::` namespace). SIMD types (`float3`, `float4x4`, etc.) cannot be read element-wise directly — use `math::store(float_array, vec)` to extract values.

Two math includes: `Core/MathTypes.h` for just type declarations (lightweight, avoids full hlslpp); `Core/Math.h` for the full library including `math::AABB` (Min/Max float3 with Expand helpers) and all hlslpp operations. Prefer the lighter include in headers.

### Camera & CameraController
`Camera` (`Engine/Graphics/Camera.h`) stores `View`, `Projection`, `ViewProjection`, and basis vectors. Update via `SetView(pos, target)` and `SetProjection(fovYRad, aspect, near, far)`. `CameraController` (`Engine/Graphics/CameraController.h`) wraps a `Camera*` and provides two modes: `FirstPerson` (WASD + RMB look) and `Orbit` (LMB rotate, MMB pan, scroll zoom). Call `controller.Update(dt, windowInput)` in `OnTick`. `Tab` toggles modes by default.

### Input system (`Engine/Platform/InputManager.h`)
`InputManager` (singleton `InputManager::Get()`) owns per-window `WindowInput` objects. Retrieve input for a window with `InputManager::GetWindowInput(windowHandle)` — returns `nullptr` if the handle isn't registered. `WindowInput` exposes:
- `IsKeyDown/Pressed/Released(KeyCode)`, `IsModifierDown(Modifier)`
- `IsMouseButtonDown/Pressed/Released(MouseButton)`
- `GetMousePosition()`, `GetMouseDelta()`, `GetScrollDelta()` — delta/scroll reset to zero each `BeginFrame`

Key codes are in `Platform/InputCodes.h`. Typical game use: `Engine::Get().GetInputManager().GetWindowInput(windowHandle)` in `OnTick`.

Cursor visibility and lock: `InputManager::SetCursorVisible(handle, bool)` / `SetCursorLocked(handle, bool)`.

### Rendering in `OnRender`
Get the per-window `CommandList` from the renderer:
```cpp
auto& renderer = Engine::Get().GetRenderer();
RenderWindowHandle rwh = Engine::Get().GetMainRenderWindowHandle();
RenderWindow* rw = renderer.GetRenderWindow(rwh);
CommandList* cmd = renderer.GetCommandList(rwh);
```

`CommandList` wraps a D3D12 graphics command list. Key methods:
- `TransitionBarrier(handle, state)` / `FlushBarriers()` — batched resource transitions
- `ClearRenderTarget(rt, color)` / `ClearDepthStencil(ds, depth, stencil)`
- `SetRenderTarget(colorRT, depthRT)` / `SetViewportAndScissor(width, height)`
- `SetPipeline(handle)` / `SetVertexBuffer(slot, handle)` / `SetIndexBuffer(handle)`
- `SetPushConstants(data, count32BitValues, destOffset)` — up to `MAX_PUSH_CONSTANT_U32S` (32) u32 values
- `Draw(...)` / `DrawIndexed(...)`

Always render to `rw->GetHDRColorBuffer()`, not the swapchain back buffer. `Renderer::EndFrame` tonemaps to the swapchain.

### Bindless rendering model
The engine uses a single global root signature with a bindless CBV/SRV/UAV heap (`GfxDevice::ResourceHeap()`) and a sampler heap. Resources are identified by `DescriptorIndex` (a `u32`; `INVALID_DESCRIPTOR = ~0u`). There are no per-draw descriptor tables — instead, pass descriptor indices to shaders via push constants with `SetPushConstants`. The HLSL side reads from `ResourceDescriptorHeap[index]` or `SamplerDescriptorHeap[index]`.

`GfxDevice::CreateSampler(desc)` returns a `DescriptorIndex` into the sampler heap. Texture and buffer `DescriptorIndex` values (SRVIndex, UAVIndex, etc.) are populated on creation and accessible from the `Texture` / `Buffer` structs via `device.Get(handle)`.

### GPU uploads (`GfxDevice::UploadContext`)
Two modes — get via `device.GetUploadContext()`:

**Synchronous** (CPU stalls until GPU copy completes — safe for init):
```cpp
ctx.Begin();
ctx.UploadBuffer(bufferHandle, data, size);
ctx.UploadTexture(textureHandle, data, size);
ctx.End();  // CPU blocks here
```

**Deferred** (data queued, flushed at next `Renderer::BeginFrame` — safe during gameplay):
```cpp
ctx.QueueBufferUpload(bufferHandle, dataVector);
ctx.QueueTextureUpload(textureHandle, dataVector);
```

### Shader pipeline
Shaders are HLSL in `Sandbox/Assets/Shaders`, compiled by the custom xmake task `compile_shaders` (`Plugins/CompileShaders/`) via **DXC**, driven by `Sandbox/ShaderBuild.json` (entry points, target profiles like `vs_6_6`, defines). It runs `after_build` of the `Sandbox` target, emitting `.cso` files next to the runtime. Models are copied from `Assets/Models` at the same time.

### Project files
A `.toml` project file (`Sandbox/Sandbox.toml`) describes app name, window settings, asset dirs, shader registrations, and `startup_scene`. It's passed to the runtime via `-p <file>` (parsed with CLI11 in `Engine/Runtime/CommandLine.h`, read with toml++).

## Conventions

- Everything lives in namespace `koi` (engine internals in `koi::internal`). Use the fixed-width aliases from `Core/Types.h` (`i32`, `u32`, `f32`, `f64`, `byte`) rather than raw `int`/`float`.
- Naming: `PascalCase` types/methods, `m_` members, `s_` statics, `g_` file-scope globals, `t_` thread-locals, `k`-prefixed constants.
- Inherit `NonCopyable` / `NonMovable` (`Core/Types.h`) to delete the respective ops.
- For bitmask enums, declare the enum then `KOI_ENABLE_ENUM_FLAGS(MyEnum)` to get `|`/`&`/`~` and the `EnumFlag<E>` wrapper (`Core/EnumFlags.h`).
- **Never include `<Windows.h>` directly** — include `Platform/Win32/Win32.h`, which pulls it in and `#undef`s the colliding macros (`CreateWindow`, `min`/`max` via `NOMINMAX`, etc.). Win32 type-stripping defines are applied project-wide in the root `xmake.lua`.
- Profiling: annotate scopes with `ZoneScoped` and frame boundaries with `FrameMark` (`Core/Profiling.h`); these compile out unless in `profile` mode.
- `FrameArray<T>` (`Graphics/Types.h`) is `std::array<T, BACK_BUFFER_COUNT>` (3) — use it for per-frame-in-flight GPU resources.
- `Match` (`Core/Patterns/Match.h`) is the overloaded-lambda visitor for `std::variant`: `std::visit(Match{ [](TypeA& a){...}, [](TypeB& b){...} }, variant)`.
- `StringUtils` (`Core/StringUtils.h`) provides UTF-8↔wide conversion, trim, split, case-insensitive compare, and `ToNumber<T>`. Always go through this rather than raw Win32 string APIs.
